# Ozon AI Аналитик

Самостоятельное веб-приложение для продавцов на Ozon: аналитика отзывов и подготовка
ответов покупателям с помощью ИИ, аналитика рекламы, карточек товаров и поисковых
запросов, многопользовательская работа с несколькими магазинами, история изменений
карточек. Продажи вне карточки товара пока архитектурно подготовлены, но не содержат
вымышленных показателей до реальной интеграции.

Это новый, независимый проект. Код и данные ранее созданных приложений (в т.ч.
`ozon-ads-analytics`) не используются, не импортируются и не подключаются.

## Статус модулей

Полностью реализовано:

- Пользователи, роли, магазины, назначение доступа, переключение магазина
- Модуль отзывов: загрузка (Ozon Seller API + CSV/XLSX), анализ ИИ, черновики,
  редактирование, подтверждение, публикация/копирование, аудит
- Аналитика отзывов (факты / рассчитанные показатели / гипотезы ИИ — раздельно)
- Карточка товара: Обзор, Отзывы, Аналитика отзывов, **Продажи** (воронка,
  конверсии, остатки, ДРР — по дням), История изменений, Рекомендации ИИ
- Настройки ответов по магазину, журнал синхронизаций, журнал действий (audit log)
- Реклама: собственные ключи Ozon Performance API на магазин, проверка
  подключения, синхронизация метаданных кампаний (название, тип, статус,
  дневной бюджет, период) через `OzonPerformanceClient`; загрузка статистики
  (расход, показы, клики, продажи, ДРР) из официального экспорта Ozon
  «Продвижение → Статистика» (CSV/XLSX) с расчётом ДРР и ROAS, страница
  «Реклама» со сводкой и разбивкой по кампаниям/товарам; список кампаний по
  вкладкам (активные / рефералка-блогеры / архив), раскрываемые строки с
  подробностями и сравнением с предыдущим днём
- Аналитика карточек товаров: загрузка официального ежедневного отчёта Ozon
  «Аналитика → Товары» (CSV/XLSX) — воронка продаж, конверсии, заказы/выкупы/
  отмены/возвраты, цена, остатки, отзывы, рейтинг, по дням; сводка и расчёт
  собственных конверсий на вкладке «Продажи» карточки товара
- Аналитика поисковых запросов: загрузка официального отчёта Ozon
  «Аналитика → Запросы» (CSV/XLSX) — по каждому запросу покупателей: сколько
  человек искало и увидело товар, позиция в выдаче, конверсии поиска в карточку
  и в заказ (значения Ozon), заказано штук/на сумму; сводка с топом запросов на
  вкладке «Поисковые запросы» карточки товара
- Дашборд — сводка по всему магазину (заказы, выручка, средний чек, расход на
  рекламу, доля расходов на рекламу в выручке, отзывы, **маржа** — см. ниже) за
  период с сравнением с предыдущим периодом такой же длины; первая страница
  после входа
- Себестоимость товара — вводится вручную один раз на карточке товара (вкладка
  «Обзор»), поскольку ни один API Ozon не отдаёт закупочную/производственную
  цену продавца — это не публичные данные. Нужна для маржи/ROI, которые
  иначе нельзя посчитать вообще ни одним способом
- Заказы/выкупы/отмены/комиссия/маржа через Ozon Seller API — автоматически, по
  расписанию (и по кнопке «Обновить заказы (авто)»), без ручной загрузки файлов.
  Страница «РНП» (сразу под «Дашбордом» в меню): по дням — заказано шт/на сумму/
  с учётом скидки, СПП (расчёт), средний чек до/после скидки, выкуплено шт/%/
  на сумму, себестоимость выкупа (только если указана на карточках всех
  проданных товаров), отменено шт/%, незавершённые заказы, комиссия Ozon,
  расход на рекламу (из уже собранной статистики рекламы) и ДРР (расчёт).
  Блок «Маржа» на Дашборде считается по тем же данным: выручка (выкуп) минус
  комиссия Ozon минус себестоимость выкупленных товаров минус расход на
  рекламу — но **только если себестоимость указана для 100% выкупленных
  товаров периода**, иначе показывается «Нет данных» вместо примерной/неверной
  цифры. Подробности подтверждённого контракта Ozon Seller API и то, чего в
  РНП намеренно ещё нет, — см. раздел «Интеграция с Ozon Seller API» ниже

Архитектурно подготовлено, но не реализовано (без фиктивных данных):

- Статистика по рекламе, карточкам товаров и поисковым запросам строго через
  API Ozon напрямую (без ручной загрузки файла) — требует асинхронного flow «создать
  отчёт → опросить статус → скачать» в Ozon Performance API, который не был
  проверен по документации в достаточной детализации для реализации без
  домыслов; статистика по рекламе, карточкам товаров и поисковым запросам
  загружается вручную из реальных экспортов Ozon (см. ниже) — для рекламы это
  период на выбор (для ежедневной детализации загружайте один отчёт на день),
  для карточек товаров разбивка уже ежедневная в самом отчёте Ozon, для
  поисковых запросов — период на выбор, как в рекламе (детализации по дням
  Ozon в этом отчёте не отдаёт)
- Воронка на странице «РНП» (переходы в карточку / положили в корзину /
  конверсия) — Ozon не отдаёт эти данные через заказы, только через отдельный
  ежедневный отчёт «Аналитика → Товары» (CSV/XLSX), который остаётся ручной
  загрузкой на странице «Товары» (см. выше)
- Логистика/хранение/штрафы/налоги/капитализация по себестоимости на странице
  «РНП» и Дашборде (как на скрине стороннего сервиса «Оцифровка») — самый
  крупный по объёму тип финансовой операции Ozon (`type="other"`, ~37% всех
  операций в тестовом окне) пока не имеет ни одного подтверждённого примера
  содержимого; нужен ещё один прогон `debug_orders_finance_api.py`, который
  захватит хотя бы одну такую операцию, прежде чем классифицировать эти суммы
  без домыслов
- Пагинация `/v3/finance/transaction/list` за пределами первой страницы — на
  реальном магазине окно в 7 дней вернуло ровно 1000 операций (= размер
  страницы), то есть операций больше и пагинация обязательна, но она ещё не
  реализована (пагинация `/v2/posting/fbo/list` и `/v3/posting/fbs/list` уже
  реализована и покрыта тестами)
- Блок «Заказы и выручка» на Дашборде по-прежнему считается из ручной загрузки
  «Аналитика → Товары» (CSV), а не из нового автосбора Ozon Seller API (блок
  «Маржа» ниже — уже из API) — сознательное решение не трогать уже работающий
  блок в этом же заходе; при необходимости переключить на единый источник
  API — уточните
- Привязка рекламных кампаний к конкретному товару в карточке товара (вкладка
  «Реклама» там пока лишь ссылается на общий список кампаний магазина)

## Технологии

Backend: Python 3.12, FastAPI, SQLAlchemy 2, Alembic, Pydantic 2, Argon2, pytest.
Frontend: React 18, TypeScript, Vite, Tailwind CSS.
БД: PostgreSQL.

## Структура репозитория

```
backend/      FastAPI-приложение (app/), requirements.txt, alembic.ini
frontend/     React + TS + Vite SPA
migrations/   Alembic-миграции (общие для всего проекта)
tests/        Pytest, включая тесты изоляции магазинов
scripts/      dev.sh (разработка), start.sh (единая команда запуска)
docker/       entrypoint.sh контейнера app, nginx.conf для TLS-оверлея
Dockerfile                  многоступенчатая сборка frontend + backend
docker-compose.yml          app + PostgreSQL
docker-compose.proxy.yml    опциональный оверлей: nginx + certbot (TLS)
README.md
.env.example
```

## Запуск в Replit

1. Импортируйте репозиторий в Replit (модули `python-3.12` и `nodejs-20`
   подключаются автоматически через `.replit`).
2. Подключите PostgreSQL (Replit Database → PostgreSQL) и добавьте `DATABASE_URL`
   в Replit Secrets.
3. Добавьте остальные секреты в Replit Secrets (Tools → Secrets), не в код и не в `.env`:
   `SESSION_SECRET`, `APP_ENCRYPTION_KEY`, `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`,
   `YANDEX_MODEL`, `AI_PROVIDER=yandex`. Для Replit Deployment дополнительно задайте
   `ENV=production` — это включает флаг `Secure` у сессионной cookie (HTTPS‑only).
4. Нажмите Run — выполнится `scripts/dev.sh` (backend с автоперезагрузкой + Vite).
5. Для Replit Deployment используется `scripts/start.sh`: он ставит зависимости,
   собирает frontend, накатывает миграции Alembic и поднимает единственный процесс
   `uvicorn`, который отдаёт и API, и собранный SPA — весь сервис запускается одной
   командой.
6. Создайте первого администратора (страницы регистрации в приложении нет — доступ
   выдаёт администратор):
   ```bash
   cd backend && source .venv/bin/activate
   python -m app.seed.bootstrap_admin admin@example.com "Имя Фамилия" пароль
   ```

## Развёртывание на своём сервере (Docker)

Для запуска вне Replit — на своём VPS или выделенном сервере — в репозитории есть
`Dockerfile` и `docker-compose.yml`: тот же принцип, что и в `scripts/start.sh` (один
процесс `uvicorn` отдаёт и API, и собранный frontend), но в контейнере и со своей
PostgreSQL рядом.

### Минимальные требования к серверу

- **CPU**: 1 vCPU для старта достаточно (один процесс uvicorn без воркеров +
  PostgreSQL на той же машине); 2 vCPU — комфортный запас, если магазинов/пользователей
  станет больше одного-двух.
- **RAM**: от 1 ГБ (PostgreSQL ~150–300 МБ, backend на Python ~150–250 МБ, плюс ОС);
  реально рекомендуется **2 ГБ**, особенно с запасом на кратковременные пики при разборе
  больших XLSX-отчётов через pandas (импорт держит весь файл в памяти).
- **Диск**: 10–20 ГБ для старта (образы Docker + база + логи); дальше растёт вместе с
  объёмом загруженных отчётов и историей отзывов — на типичных объёмах одного магазина
  рост медленный (десятки МБ в месяц), но стоит иметь план по мониторингу места.
- **ОС**: любой Linux с Docker Engine 24+ и Docker Compose plugin (протестировано на
  Ubuntu 22.04/24.04 LTS). GPU не нужен — обращения к ИИ идут во внешний Yandex AI
  Studio API, локальная модель не запускается.
- **Сеть**: публичный IP, открытые порты 80/443 (для TLS-прокси) либо только 8000, если
  сервис будет за уже существующим реверс-прокси или доступен только по VPN/приватной сети.

Один сервер такого размера спокойно тянет несколько магазинов при типичной для малого/
среднего продавца нагрузке; рост требований в первую очередь придётся на PostgreSQL при
накоплении больших объёмов отзывов/статистики — тогда есть смысл вынести БД на отдельную
машину или взять управляемый PostgreSQL.

### Быстрый старт

```bash
git clone <URL вашего форка/репозитория>
cd ozon-analytics_rk
cp .env.example .env
```

Заполните `.env`: `POSTGRES_PASSWORD` (произвольный пароль для контейнера БД —
обязателен, `docker compose` откажется стартовать без него), `SESSION_SECRET` и
`APP_ENCRYPTION_KEY` (команды для генерации — см. комментарии в `.env.example`),
`AI_PROVIDER`/`YANDEX_*` (или `AI_PROVIDER=demo` без реального ИИ-провайдера),
`ENV=production`, `CORS_ORIGINS` — домен/адрес, с которого будет открываться
приложение. `DATABASE_URL` в `.env` для Docker-запуска не используется —
`docker-compose.yml` строит его сам из `POSTGRES_*` и указывает на контейнер `db`.

**Если запускаете без TLS** (пока только по IP, без домена и nginx-оверлея —
см. следующий раздел) — обязательно добавьте `SESSION_COOKIE_SECURE=false`.
`ENV=production` сам по себе включает флаг `Secure` у сессионной cookie, а
браузер никогда не отправляет `Secure`-cookie обратно по обычному HTTP: вход
будет казаться успешным (`/api/auth/login` вернёт `200`), но каждый следующий
запрос будет молча получать `401` — ни ошибки на экране, ни очевидной причины,
просто ничего не работает после первого клика. Это реальная ошибка, на
которую напоролись при первом боевом развёртывании этого проекта — не
гипотетическая. Как только заведёте домен и TLS (раздел ниже), уберите
`SESSION_COOKIE_SECURE` из `.env` совсем — тогда `ENV=production` снова сам
включит `Secure`, что и требуется при HTTPS.

```bash
docker compose up -d --build
```

Поднимутся два контейнера: `db` (PostgreSQL 16 с volume `db_data` — данные переживают
пересборку и перезапуск) и `app` (собирает frontend, накатывает миграции Alembic при
каждом старте контейнера через `docker/entrypoint.sh`, поднимает uvicorn). Приложение
будет доступно на `http://<адрес сервера>:8000`. Проверить, что всё поднялось:

```bash
curl http://localhost:8000/api/health
```

Создайте первого администратора (без него в приложение попасть некому):

```bash
docker compose exec app python -m app.seed.bootstrap_admin admin@example.com "Имя Фамилия" пароль
```

### TLS на своём домене (nginx + Let's Encrypt)

Порт 8000 напрямую без TLS годится для теста или для работы за уже существующим
прокси/VPN, но не для боевой эксплуатации с реальными паролями и данными. Для
терминации TLS в комплекте есть оверлей `docker-compose.proxy.yml` (nginx + certbot):

1. В `docker/nginx.conf` замените `YOUR_DOMAIN` на реальный домен (два места).
2. Направьте DNS A-запись домена на IP сервера.
3. Первичный выпуск сертификата (webroot-режим, порт 80 должен быть свободен и открыт):
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.proxy.yml up -d db app nginx
   docker compose -f docker-compose.yml -f docker-compose.proxy.yml run --rm certbot \
     certonly --webroot -w /var/www/certbot -d YOUR_DOMAIN --email you@example.com --agree-tos --no-eff-email
   docker compose -f docker-compose.yml -f docker-compose.proxy.yml restart nginx
   ```
4. Продление сертификата не автоматизировано контейнером certbot (он не крутит цикл
   сам) — добавьте в cron/systemd-таймер на хосте раз в день-два:
   ```bash
   docker compose -f docker-compose.yml -f docker-compose.proxy.yml run --rm certbot renew \
     && docker compose -f docker-compose.yml -f docker-compose.proxy.yml exec nginx nginx -s reload
   ```

С этим оверлеем `app` перестаёт слушать порт 8000 на всех интерфейсах (только
`127.0.0.1`) — наружу торчит только nginx на 80/443.

### Резервное копирование и обновление

```bash
# бэкап БД (том db_data не даёт файловой копии — дамп через pg_dump внутри контейнера)
docker compose exec db pg_dump -U ozon_app ozon_analytics > backup_$(date +%F).sql

# восстановление
cat backup_2026-09-04.sql | docker compose exec -T db psql -U ozon_app ozon_analytics

# обновление на новую версию кода
git pull
docker compose up -d --build   # миграции Alembic накатятся автоматически при старте
```

### Ограничение проверки в этой сессии

Собрать образ и реально поднять контейнеры в этой (песочничной) сессии не удалось —
исходящий сетевой доступ к CDN Docker Hub (`production.cloudfront.docker.com`, откуда
тянутся слои базовых образов `python:3.12-slim`/`node:20-alpine`) заблокирован политикой
исходящего трафика этой среды. Проверено то, что было доступно: `docker compose config`
(включая merge с `docker-compose.proxy.yml` — override портов через `!override`
подтверждён рабочим на установленной здесь версии Docker Compose), синтаксис
`docker/entrypoint.sh` (`bash -n`), и путь `frontend/dist` в многоступенчатой сборке
подобран так, чтобы совпасть с тем, что уже проверено в `scripts/start.sh`/Replit
(`Path(__file__).resolve().parents[2]` в `app/main.py` указывает на `/app` при раскладке
`/app/backend/app/main.py` + `/app/frontend/dist`). Перед боевым использованием
рекомендуется один раз прогнать `docker compose up -d --build` на реальном сервере с
доступом в интернет и свериться с логами.

## Локальный запуск

```bash
cp .env.example .env   # заполните переменные, .env не коммитится
bash scripts/dev.sh
```

Backend поднимется на `:8000`, frontend (dev-сервер Vite с проксированием `/api`) — на `:5173`.

## Тесты

```bash
cd backend && source .venv/bin/activate
pip install -r requirements.txt
cd ..
pytest
```

Тесты требуют доступную PostgreSQL (`DATABASE_URL` из окружения тестов); используемая
для тестов база данных пересоздаётся при каждом запуске. Отдельный набор тестов
(`tests/test_store_isolation.py`) проверяет, что пользователь одного магазина не может
получить отзывы, товары, ответы или настройки другого магазина ни при каком прямом
API-запросе, включая случай, когда пользователь сам подставляет чужой `store_id`.

### Ручная сквозная проверка (E2E smoke test)

`scripts/e2e_smoke_test.py` — дополнительный ручной прогон поверх реально запущенного
backend (не заменяет pytest, а проверяет то же самое живьём, через HTTP): загрузка
CSV, анализ ИИ, генерация и правка черновика, обязательное подтверждение перед
публикацией, корректная деградация публикации без реальных ключей Ozon, и полный
набор проверок изоляции двух магазинов между собой. Полезен после инфраструктурных
изменений или перед деплоем. Требует только `httpx` (уже есть в зависимостях backend).

```bash
# backend должен быть запущен и доступен (см. «Локальный запуск» выше),
# первый администратор должен быть создан через bootstrap_admin
E2E_ADMIN_EMAIL=admin@example.com E2E_ADMIN_PASSWORD=пароль \
    python scripts/e2e_smoke_test.py
```

Скрипт создаёт тестовые магазины/пользователей/отзывы с уникальным суффиксом при
каждом запуске (безопасно перезапускать без сброса базы) и печатает `PASS`/`FAIL`
по каждой проверке, завершаясь с ненулевым кодом при любом провале.

## Роли и доступ

- **admin** — платформенный администратор: видит и переключает все магазины, создаёт
  пользователей, назначает доступ.
- **owner** — полный доступ к своему магазину(ам).
- **manager** — работает с отзывами, ответами, синхронизацией.
- **viewer** — только просмотр.

Доступ к `store_id` проверяется backend'ом на каждом запросе по сессии текущего
пользователя — `store_id`, переданный с frontend, никогда не считается источником
истины сам по себе.

**Исключение из иерархии ролей**: вводить/менять API-ключи Ozon (Seller API и
Performance API, страница «Подключение к Ozon») может только **admin** —
даже пользователь с ролью **owner** на конкретном магазине этого не может
(`require_platform_admin_for_store` в `app/api/deps.py`). Роль owner нужна
сотруднику для полноценной работы с магазином, но сами секретные ключи
доступа к API Ozon — более чувствительные данные, и их сознательно оставили
только за реальным администратором платформы. Просмотр статуса подключения
(настроены ли ключи, когда была последняя проверка) и кнопка «Проверить
подключение» по-прежнему доступны роли owner — им закрыт только сам ввод
новых значений.

## Демонстрационный режим

При `DEMO_MODE=true`: реальные обращения к Ozon API не выполняются, публикация
ответов отключена, ИИ-провайдер по умолчанию — встроенный `DemoProvider`
(офлайн, без обращений к сети), а результаты явно помечены как демонстрационные.
Демо-данные не пересекаются с реальными (поле `is_demo` у отзывов).

## Безопасность секретов

- Ключи Ozon (`Client-Id`, `Api-Key`) каждого магазина хранятся в БД в зашифрованном
  виде (Fernet, ключ — `APP_ENCRYPTION_KEY` из Replit Secrets) и никогда не
  возвращаются на frontend целиком — только маскированное превью.
- Пароли пользователей хешируются Argon2.
- Сессия — подписанный HttpOnly-cookie, не localStorage.
- `.env` и любые файлы с секретами исключены из git (`.gitignore`).

## Интеграция с Ozon Seller API

`backend/app/services/ozon/client.py` — единственное место в коде, которое обращается
к `https://api-seller.ozon.ru`. Используются методы `/v1/review/list`, `/v1/review/info`,
`/v1/review/comment/list`, `/v1/review/comment/create` — они документированы Ozon как

### Заказы и финансы (Seller/Finance API) — контракт подтверждён на реальном магазине

`list_fbo_postings()` (`POST /v2/posting/fbo/list`), `list_fbs_postings()`
(`POST /v3/posting/fbs/list`) и `list_finance_transactions()`
(`POST /v3/finance/transaction/list`) — точный контракт подтверждён прогоном
`backend/scripts/debug_orders_finance_api.py` на реальном магазине (см. описание
скрипта ниже). Подтверждено и используется в `order_daily_sync_service.py`:

- Оба метода посортировки (`/v2/posting/fbo/list`, `/v3/posting/fbs/list`)
  отдают одинаковую форму: `result.postings[]` (+ `result.has_next` для
  пагинации — реализована, `MAX_PAGES=50`, `PAGE_LIMIT=1000`) с полями
  `order_number`, `status` (подтверждены значения `"delivered"`, `"cancelled"`,
  остальное — трактуется как «незавершённый»), `in_process_at`, `products[]`
  (`sku`, `offer_id`, `quantity`, `price` — строка, фактическая цена продажи со
  скидкой).
- `financial_data.products[]` — сопоставляется со строкой `products[]` по
  `product_id == sku`; используются `commission_amount` (отрицательное число) и
  `old_price` (цена ДО скидки — из неё считается «Заказано на сумму» и СПП на
  странице «РНП»).
- **Важное расхождение FBO/FBS**: в `analytics_data` название склада — это
  `warehouse_name` у FBO, но `warehouse` (другой ключ!) у FBS. В текущей
  синхронизации `analytics_data` вообще не используется (только постатейно
  замечено на будущее), но при дальнейшей работе с этим полем — не путать ключи.
- `/v3/finance/transaction/list` отдаёт `result.operations[]` — подтверждённые
  типы (`type`): `orders` (обычная продажа: `accruals_for_sale`,
  `sale_commission`, `posting`, `items[]`, `services[]`), `returns` (структура
  та же, `accruals_for_sale=0`), `services` (сервисные начисления/списания без
  привязки к конкретному заказу — `posting.delivery_schema=""`, `items=[]`).
  **`type="other"` (~37% всех операций в тестовом окне, самый крупный тип) пока
  без единого подтверждённого примера** — не используется нигде в расчётах,
  пока не появится реальный пример. Финансовые транзакции сейчас в
  синхронизации не используются вовсе (только комиссия — из `financial_data`
  внутри самих постингов, не из этого метода); эта часть API — задел на
  Логистику/Хранение/Штрафы/Налоги, когда появится пример `type="other"` и
  будет реализована пагинация (см. ниже).
- Пагинация `/v3/finance/transaction/list` **не реализована** — на реальном
  магазине окно в 7 дней вернуло ровно 1000 операций (= `page_size`), то есть
  операций достоверно больше одной страницы.

Ответ по-прежнему разобран нестрого (`OzonPostingListResponse`/
`OzonFinanceTransactionListResponse` в `app/services/ozon/schemas.py`:
`extra="allow"`, все поля опциональны, кроме тех, что перечислены выше как
подтверждённые и используемые) — часть полей ответа (например, вложенный
`requirements` у FBS, `tariffication`, весь `analytics_data`) присутствует в
реальном ответе, но осознанно не используется, пока не появится конкретная
задача, которая их требует.

Диагностический скрипт `backend/scripts/debug_orders_finance_api.py` при
повторном прогоне на реальном магазине выводит не построчный дамп (на реальном
магазине это были тысячи строк), а сжатую сводку: общее количество найденных
заказов/операций и по одному полному примеру каждой встретившейся «формы» —
одна запись для FBO, одна для FBS, и по одному примеру на каждое значение поля
`type` у финансовых операций (до 12 типов). Чтобы получить пример для
`type="other"`, нужен ещё один прогон — в последнем реальном выводе такой
пример не встретился:

```
docker compose exec app python backend/scripts/debug_orders_finance_api.py --store-id <id>
```

### Ручная загрузка отзывов (CSV/XLSX) — формат реального экспорта Ozon

`backend/app/services/review_import.py` разбирает файл, скачанный на странице «Отзывы»
личного кабинета Ozon («Отзывы → Скачать отчёт»). Формат подтверждён на реальном
файле, после того как загрузка молча не давала эффекта на реальном магазине:

- **`;`-разделитель, UTF-8 с BOM** — не запятая, которую `pandas.read_csv` использует по
  умолчанию; из-за этого любая ячейка с запятой внутри текста (например, название
  товара «Складной пуф, размер 30×30, серый») ломала разбор целиком с ошибкой парсера.
  Импортёр сначала пробует `;`, и только если это дало не больше одной колонки —
  откатывается на `,` (для простого, вручную составленного файла).
- **Колонки «Артикул» и «SKU» — это ДВЕ разные колонки**, не синонимы: «Артикул» — это
  собственный офер-id продавца (например, `пуф/S/сер1/2`), а «SKU» — настоящий числовой
  SKU Ozon, по которому в приложении ищется/создаётся товар. Раньше оба названия
  считались взаимозаменяемыми алиасами одного поля, и то, какая колонка «побеждала»,
  зависело от непредсказуемого порядка перебора Python `set` — в реальном файле это
  иногда приводило к тому, что вместо числового SKU использовался текстовый артикул.
- **В реальном экспорте нет отдельной колонки «ID отзыва»** — только «Номер заказа»
  (формат вроде `0225485653-0073`), «Артикул», «SKU», «Название товара», «Статус
  получения», «Текст отзыва», «Дата публикации», «Статус отзыва», «Оценка», «Количество
  фото/видео/ответов на отзыв». Так как один заказ у Ozon соответствует одному отзыву
  (подтверждено — номер заказа уникален в реальном файле из 473 строк), номер заказа
  используется как замена ID отзыва (с префиксом `order:`, чтобы не пересечься с
  настоящими ID отзывов из API-синхронизации, которые всегда UUID).

Пока такого файла руки не касались реальные — только вручную собранный простой шаблон
(`ozon_review_id`/`sku`/`оценка`/...) — что и позволило этой проблеме остаться
незамеченной. Регрессионные тесты в `tests/test_review_import.py` собраны на основе
именно реального файла.

## Интеграция с Ozon Performance API (реклама)

`backend/app/services/ozon_performance/client.py` — единственное место в коде, которое
обращается к `https://api-performance.ozon.ru` (актуальный хост; старый
`performance.ozon.ru` выведен из эксплуатации). Отдельная от Seller API пара ключей
(Client-Id/Client-Secret, OAuth `client_credentials`), отдельное хранение и отдельная
проверка подключения на магазин. Реализовано: обмен токена (`POST /api/client/token`)
и получение списка кампаний (`GET /api/client/campaign`) — название, тип, статус,
дневной бюджет, период; поля разбираются защитно (`extra="allow"`, без домыслов о
неподтверждённых форматах, например единицах бюджета). Синхронизация сохраняет эти
метаданные в `advertising_campaigns`. Асинхронный flow «запрос отчёта → опрос статуса →
скачивание» ежедневной статистики (клики/показы/расход/заказы) тоже реализован — его
точный контракт (см. следующий раздел) был подтверждён на реальном аккаунте перед
реализацией.

### Статистика рекламы (расход, показы, клики, ДРР, ROAS)

Помимо автоматического сбора через Performance API (следующий раздел), статистику можно
загрузить из **реального, проверенного** источника — официального экспорта личного
кабинета Ozon («Продвижение → Статистика → Скачать отчёт», CSV/XLSX). Формат разобран и
покрыт тестами на основе настоящего файла (`tests/fixtures/ozon_advertising_statistics_sample.xlsx`,
183 строки): одна строка на пару SKU+кампания за выбранный период (не за день — этот
отчёт не отдаёт разбивку по дням; для ежедневной детализации загружайте один отчёт в
день, с периодом в одни сутки). Лист `Union` (продажи по объединённым карточкам)
намеренно не импортируется — его суммирование с основным листом задвоило бы выручку.

`backend/app/services/advertising_import.py` разбирает файл защитно (переносимые
заголовки, значения `''`/`-` трактуются как отсутствующие, а не как ноль).
`backend/app/services/advertising_analytics_service.py` считает ДРР и ROAS:

```
ДРР (%) = расход / продажи в продвижении × 100
ROAS    = продажи в продвижении / расход
```

Оба показателя — `None` (не 0), если расход или продажи равны нулю/отсутствуют.
Проценты ДРР, которые Ozon указывает в самом отчёте построчно
(`drr_promo_pct_ozon`/`drr_total_pct_ozon`), сохраняются как есть и никогда не
пересчитываются; агрегированные ДРР/ROAS в аналитике — только те, что рассчитаны этим
приложением (сумма расходов / сумма продаж), поскольку построчные проценты Ozon
некорректно усреднять напрямую.

Список кампаний на странице «Реклама» разбит на три вкладки: активные, «Рефералка/
блогеры» (`campaign_type` = `REF_VK`/`REF_BLOGGER` — не обычная платная реклама) и
«Архив» (`state` = `CAMPAIGN_STATE_ARCHIVED`), чтобы они не смешивались с текущими
активными кампаниями. Строка кампании раскрывается по клику: `GET
/advertising/campaigns/{id}/detail` (`compute_campaign_detail` в
`advertising_analytics_service.py`) суммирует расход/показы/клики/продажи по всем
загруженным строкам этой кампании и, если для неё есть **минимум два отдельных
дневных отчёта** (`period_start == period_end` на две разные даты), считает сравнение
последнего дня с предыдущим — стрелка и цвет (зелёный/красный) показывают рост или
падение каждого показателя. Если дневных отчётов меньше двух (например, загружен
только недельный/месячный период), сравнение не показывается — оно не подделывается
из данных другой длины периода, вместо графика/цифр показывается прямое объяснение
почему сравнения нет.

### Автоматический сбор статистики рекламы (Performance API, без CSV)

Клики/показы/CTR/расход/заказы/выручка по дням можно собирать **автоматически**, без
ручной загрузки CSV — по кнопке «Обновить статистику (авто)» на странице «Реклама» и
раз в сутки по расписанию (`APScheduler`, `backend/app/services/advertising_daily_scheduler.py`).
Источник — асинхронный flow Ozon Performance API (`запрос отчёта → опрос статуса →
скачивание ZIP`), чей точный контракт подтверждён на реальном аккаунте перед реализацией:

- **до 10 ID кампаний за один запрос** `POST /api/client/statistics` — это жёсткий лимит
  Ozon, а не выбор приложения; активные кампании (`CAMPAIGN_STATE_RUNNING`) бьются на
  батчи по 10 и обрабатываются **строго последовательно**
  (`backend/app/services/advertising_daily_sync_service.py`) — запрос отчёта для
  следующего батча отправляется только после того, как предыдущий скачан и сохранён;
- **не более 1 отчёта одновременно на аккаунт** — повторный запрос отчёта, пока
  предыдущий не завершён, возвращает ошибку (подтверждённый текст: «Превышен лимит
  активных запросов (максимум 1)»); эта ошибка распознаётся отдельно
  (`OzonPerformanceReportBusy`) и обрабатывается повтором с паузой, а не как фатальный
  сбой всей синхронизации;
- отчёт — **ZIP с одним CSV на кампанию**, имя файла `{ID кампании}_{датаОт}-{датаДо}.csv`
  (ID кампании берётся из имени файла, а не из колонки); внутри — `;`-разделитель,
  строка заголовка отчёта, строка с колонками, строки по дням/SKU и финальная строка
  «Всего», которая не импортируется (та же логика, что и для строки «Итого и среднее» в
  импорте карточек товаров — обнаруживается по нефактическому значению в колонке
  «День», а не по фиксированному номеру строки);
- **кодировка не гарантирована** — на практике встречались и UTF-8 с BOM, и
  Windows-1251; парсер (`backend/app/services/advertising_daily_statistic_parser.py`)
  пробует `utf-8-sig`, затем откатывается на `cp1251`;
- **`dateFrom`/`dateTo` в теле запроса — ISO (`YYYY-MM-DD`), а не `ДД.ММ.ГГГГ`**,
  несмотря на то что даты в имени файла отчёта внутри ZIP — именно `ДД.ММ.ГГГГ`; это два
  независимых, разных формата. Подтверждено на реальном аккаунте: значение `ДД.ММ.ГГГГ`
  в теле запроса Ozon отклоняет с `{"error": "bad request parameter: dateFrom"}`;
- токен OAuth действует ~30 минут — `OzonPerformanceClient` обновляет его заранее и
  при любом 401, так что истечение токена посреди долгой синхронизации обрабатывается
  тем же механизмом, без отдельной логики в воркере.

**Колонки «Заказы»/«Выручка»/ДРР — подтверждено на реальном аккаунте.** Первая версия
`_COLUMN_MAP` (в `advertising_daily_statistic_parser.py`) использовала названия колонок
«Заказы»/«Выручка, ₽», перенесённые по аналогии с ручным XLSX-экспортом «Продвижение →
Статистика» — из-за этого расход/показы/клики парсились верно, а заказы/выручка/ДРР
оставались пустыми для всех кампаний. Диагностика через
`backend/scripts/inspect_advertising_daily_raw_payload.py` (читает
`advertising_daily_statistics.raw_payload` — необработанный CSV-ряд Ozon, который парсер
сохраняет ещё до применения `_COLUMN_MAP`, так что новый запрос к Ozon не понадобился)
на реальном магазине показала настоящие названия: **«Продано товаров»** (заказы),
**«Продажи в продвижении, ₽»** (выручка), **«ДРР в продвижении, %»** и
**«ДРР (общий), %»** — теперь именно они в `_COLUMN_MAP`. Как и для `AdvertisingStatistic`,
эти два процента ДРР от Ozon сохраняются в БД как есть (`drr_promo_pct_ozon`/
`drr_total_pct_ozon` в `AdvertisingDailyStatistic`) и никогда не пересчитываются — но
таблица «по дням» на странице «Реклама» показывает рассчитанный этим приложением ДРР
(расход/выручка, просуммированные по всем SKU кампании за день), а не эти построчные
проценты Ozon, потому что усреднять построчные проценты при суммировании по нескольким
SKU было бы некорректно (тот же принцип, что уже описан выше для агрегированной
аналитики по ручному CSV-экспорту). `orders_model`/`revenue_model_rub` остаются
неподтверждёнными для этого источника — та же диагностика их не подтвердила и не
опровергла, эти два поля продолжают заполняться только если реальная колонка когда-нибудь
совпадёт по названию.

Результат сохраняется в отдельную таблицу `advertising_daily_statistics`
(`AdvertisingDailyStatistic`), а не в ту же, что CSV-загрузка (`AdvertisingStatistic`) —
**сознательно**: наборы колонок разные (здесь есть тип страницы/условие показа/средняя
ставка, в CSV-отчёте — процент ДРР и стоимость клика), и если для одной кампании и
периода данные есть в обоих источниках, их сложение задвоило бы расход и выручку. На
странице «Реклама» это отдельная таблица «Автоматически собранная статистика», без
смешения с загруженными вручную строками. Настройки — `ADVERTISING_STATS_BATCH_SIZE`,
`ADVERTISING_STATS_POLL_INTERVAL_SECONDS`, `ADVERTISING_STATS_POLL_TIMEOUT_SECONDS`,
`ADVERTISING_STATS_DEFAULT_LOOKBACK_DAYS` (по умолчанию — последние 7 дней при запуске
без явного периода, включая ежедневный автозапуск), `ADVERTISING_STATS_SCHEDULER_ENABLED`,
`ADVERTISING_STATS_SCHEDULER_HOUR_UTC` (см. `backend/app/core/config.py`).

Ручной запуск — `POST /api/stores/{id}/sync/ozon-advertising-statistics` — выполняется в
фоне (`FastAPI BackgroundTasks`, со своей БД-сессией, а не сессией запроса, так как
синхронизация может занимать несколько минут) и сразу возвращает `SyncRun` со статусом
`running`; фронтенд опрашивает `GET /sync/runs`, пока статус не изменится — тот же
журнал синхронизаций, что и у остальных источников данных.

### Аналитика карточек товаров (воронка продаж, конверсии, остатки, ДРР)

Так же, как со статистикой рекламы: вместо непроверенного API — реальный, проверенный
источник, официальный экспорт «Аналитика → Товары» (лист «По товарам», CSV/XLSX).
В отличие от рекламной статистики, здесь Ozon **уже отдаёт разбивку по дням** (колонка
«День») — полноценная ежедневная детализация без компромиссов. Формат разобран и
покрыт тестами на основе настоящего файла (7 дней по одному товару); реальный файл в
репозиторий не включён, так как содержит название продавца — вместо него
`tests/fixtures/ozon_product_card_analytics_sample.xlsx` с той же структурой заголовков
и обезличенными данными.

Заголовки в этом отчёте — двухуровневые, со слитыми ячейками (у части колонок название
только в верхней строке, у остальных — в подстроке; недостающая подстрока читается как
`NaN`, а не `None`, что важно учитывать при разборе через pandas), и включают дату
периода прямо в текст заголовка — при разборе она вырезается регулярным выражением, чтобы
файл читался независимо от периода экспорта. Строка «Итого и среднее» и пояснительная
строка над данными пропускаются по признаку «колонка "День" не парсится как дата», а не
по фиксированному номеру строки.

`backend/app/services/product_analytics_import.py` — разбор; те же три известных бага
регистра атрибутов у экспортёра (`app/services/xlsx_compat.py`), что и в статистике
рекламы, встретились и здесь (`horizontal="Left"`, `activePane="bottom-right"`) — чинятся
той же терпимой загрузкой XLSX, теперь применяемой во всех трёх импортёрах (отзывы,
реклама, карточки товаров).

`backend/app/services/product_analytics_service.py` считает свои агрегаты — суммы по
дням плюс несколько отношений (добавления в корзину / показы, заказы / добавления в
корзину, выкуплено / заказано). Это **не попытка воспроизвести** формулу самого Ozon:
на реальных данных было видно, что построчная «Конверсия из корзины в заказ» у Ozon не
равна простому отношению заказов к добавлениям в корзину той же строки — точная методика
не раскрыта, поэтому приложение считает собственное, чётко документированное отношение,
а не выдаёт его за показатель Ozon. Корректность самого суммирования (аддитивных полей)
подтверждена независимо: сумма по 7 дням совпала до знака с строкой «Итого и среднее»,
которую Ozon сам приводит в файле (эта строка не импортируется как факт — используется
только как сверка при разработке).

### Аналитика поисковых запросов (показы/заказы по каждому запросу покупателей)

Так же, как со статистикой рекламы и карточек товаров: вместо непроверенного API —
реальный, проверенный источник, официальный экспорт «Аналитика → Запросы» (лист
«Запросы моего товара», CSV/XLSX). Формат разобран и покрыт тестами на основе
настоящего файла (150 уникальных запросов по одному товару); реальный файл в
репозиторий не включён (в нём реальный SKU и название товара — в отличие от файла
карточек товаров, здесь нет отдельного поля с именем продавца, но сам товар всё
равно идентифицирующие данные), вместо него
`tests/fixtures/ozon_search_queries_sample.xlsx` с той же структурой и обезличенными
данными.

В отличие от обоих предыдущих отчётов, этот файл **не плоская таблица** — это
иерархический блок: одна строка-«шапка товара» (SKU, Артикул, Название товара,
остальные колонки пустые), за которой сразу следуют все строки-запросы этого товара
(SKU/Артикул/Название пустые, заполнены только текст запроса и метрики), затем
шапка следующего товара и так далее. `backend/app/services/search_query_import.py`
переносит идентификацию текущего товара вперёд по строкам-запросам, пока не
встретится следующая строка-шапка. Дата в файле — только периодом (строки
«Дата начала:» / «Дата конца:» в метаблоке в начале листа, формат ДД/ММ/ГГГГ), как в
статистике рекламы: разбивки по дням Ozon в этом отчёте не отдаёт.

Ещё одно отличие от предыдущих двух отчётов: здесь **каждая метрика — уже готовый
текст**, а не число. Числа с разделителем разрядов через пробел (`'185 862'`, в файле
это может быть обычный пробел, неразрывный U+00A0 или узкий неразрывный U+202F —
все три варианта встретились в реальном файле), проценты через запятую со знаком `%`
(`'2,98%'`), суммы в рублях со знаком `₽` (`'72 650 ₽'`). Под это заведён отдельный
разбор `clean_ru_formatted_number`/`clean_ru_formatted_int` в
`backend/app/services/import_common.py` — существующий `clean_number` эти форматы не
понимает (нет разбора разделителя разрядов и суффиксов), поэтому не переиспользован
как есть. Попутно найден и исправлен реальный баг в общем `clean_str`: он не отличал
пустую ячейку pandas (`NaN`, тип `float`) от текста — `str(float('nan'))` даёт строку
`"nan"`, которая проходила как непустое значение. Из-за этого «шапка товара» и
строки-запросы неотличимо путались при разборе (ячейка SKU в строке-запросе читалась
как непустая); чинится проверкой `pd.isna()` до приведения к строке — исправление
общее, затрагивает все импортёры, использующие `clean_str` на сырых ячейках pandas.

Проценты, которые Ozon отдаёт построчно (`conv_search_to_card_pct_ozon`,
`conv_search_to_order_pct_ozon`), сохраняются как есть в том виде, в котором их
показывает файл (`"2,98%"` → `2.98`, то есть уже сами проценты, а не доля 0..1 — в
отличие от одноимённых по смыслу полей в карточках товаров, где исходные ячейки Excel
хранят именно долю). `backend/app/services/search_query_analytics_service.py` считает
только собственную, чётко документированную конверсию (заказано штук / сумма «человек
искало») — на реальных данных она отличается от построчной «Конверсии из поиска в
заказ» Ozon на два порядка (761 251 суммарных «искало» против 115 заказов на весь
файл дают 0,015%, тогда как Ozon в файле для отдельных строк указывает проценты вида
0,08–0,15%), то есть методика Ozon явно считает знаменатель не как сырое число
поисков — точная формула не раскрыта, поэтому приложение не выдаёт свой расчёт за
показатель Ozon.

## Позиции в поиске (динамика позиции товара по запросам)

Отдельная вкладка «Позиции в поиске» показывает, на каком месте товары находятся в
поисковой выдаче Ozon по каждому запросу, с историей по датам и подсветкой изменения
(зелёный — товар поднялся, красный — опустился).

**Проверка через API (сделана в первую очередь, как и требовалось).** В Ozon Seller
API действительно существует пара методов — `POST /v1/analytics/product-queries`
(общая аналитика) и `POST /v1/analytics/product-queries/details` (детализация по
запросу), эквивалент раздела «Аналитика → Товары в поиске → Запросы моего товара»;
метод вышел из беты 23 июля 2025. Но точный контракт запроса/ответа подтвердить не
удалось: `docs.ozon.ru`, `dev.ozon.ru`, `habr.com`, `postman.com` заблокированы сетевым
прокси в этой рабочей среде, а все проверенные сторонние SDK (Go/Python) старше даты
выхода метода из беты и его ещё не реализуют. **Автосбор через API поэтому не
реализован** — это тот случай из ТЗ, когда метод есть, но контракт не подтверждён; при
желании его добавить нужно сначала прислать реальный `curl`-ответ (структура запроса
для проверки описана в истории чата этой сессии).

**Реализован вариант с ручной загрузкой — и он оказался не новой функциональностью.**
При разборе задачи выяснилось, что этап 9 («Аналитика поисковых запросов») уже
парсит **тот же самый файл** («Аналитика → Запросы», лист «Запросы моего товара») в
таблицу `search_query_statistics` (`backend/app/models/search_query_statistic.py`), и
эта таблица уже хранит `position_ozon` — то есть позицию по каждому запросу. Отдельная
таблица `search_query_positions`, которую предполагало ТЗ, не понадобилась: каждая
загрузка уже добавляет новую дату среза (`period_end`) вместо перезаписи (проверено
на реальном файле `sellerqueries_08.08-04.09.2026...xlsx`: 156 строк запросов для
одного SKU, 0 ошибок разбора), так что история по датам уже накапливалась — не хватало
только сравнения между срезами.

Добавлено:
- `compute_search_query_positions` (`backend/app/services/search_query_analytics_service.py`)
  — для каждой пары (SKU, запрос) берёт два самых свежих среза по `period_end` и
  считает разницу: `position_change = позиция_в_прошлый_раз − текущая_позиция`;
  положительное значение = товар поднялся (число позиции уменьшилось) → зелёная
  стрелка вверх; отрицательное — красная стрелка вниз; если предыдущего среза нет —
  честно «нет данных для сравнения», а не поддельный ноль. Фильтр по тексту запроса
  применяется уже после сравнения, чтобы не терять историческую точку сравнения.
- `GET /api/stores/{id}/search-queries/positions` — отдаёт готовый список для таблицы;
  загрузка файла — тот же существующий `POST /search-queries/upload`, что и раньше.
- Вкладка «Позиции в поиске» (`frontend/src/pages/SearchPositionsPage.tsx`): таблица
  Товар/Запрос/Текущая позиция/Позиция в прошлый раз/Изменение/Показы/Заказы,
  зелёная/красная подсветка изменения, поиск по товару и по запросу (мгновенный,
  на стороне браузера), растягиваемые колонки — тем же переиспользуемым хуком
  `frontend/src/hooks/useResizableColumns.ts`, вынесенным туда из страницы «Реклама»,
  чтобы не дублировать код.

**Проверено сквозным тестом на обоих присланных реальных файлах** (через Playwright,
реальные backend+frontend, не моки): `sellerqueries_08.08-04.09.2026...xlsx` даёт 156
строк с позициями без единой ошибки разбора; вторая, изменённая копия того же файла
(другой период, две изменённые позиции) корректно показала `▲ 16` зелёным для
улучшенного запроса, `▼ 13` красным для ухудшившегося и «без изменений» для всех
остальных — то есть сравнение действительно работает на структуре реального файла, а
не на синтетических данных.

### Дополнительно: конкуренты по запросу («Результаты по запросу»)

Второй присланный файл — `explainer_report_...xlsx` — это другой отчёт: полная выдача
по одному запросу с конкурентами (позиция, продавец, цена, отзывы, ставки за
клик/заказ, соответствие запросу, индекс цен). Как и указано в ТЗ, сделан отдельным,
более простым экраном — вкладка «Конкуренты по запросу» на той же странице, но без
интеграции в логику истории/подсветки позиций: у отчёта по конкурентам нет
естественного ключа для истории (это выдача по всему рынку на один запрос, а не
данные по одному товару продавца), поэтому сравнивать его на текущий момент не с чем.
`backend/app/services/search_query_competitors_service.py` разбирает файл **без
сохранения в БД** — эндпоинт `POST /search-queries/competitors/preview` возвращает
разобранный отчёт напрямую в ответе, ничего не пишет в базу. Проверено на реальном
файле `explainer_report_06-09-2026_15-16-52.xlsx`: 110 строк выдачи по запросу
«обувница» разобраны без ошибок, включая специфичные для этого отчёта пропуски
(`«—»`/`«Выключено»` в колонке ставки за заказ — не все продавцы используют этот
инструмент продвижения).

## Дашборд (сводка по магазину, GET /api/stores/{id}/dashboard)

Первая страница после входа — сводка ключевых показателей, которые обычно
ежедневно проверяют владельцы/руководители: заказы, выручка, средний чек,
расход на рекламу, отзывы, за выбранный период (по умолчанию — последние
`DASHBOARD_DEFAULT_LOOKBACK_DAYS` дней, 30) с сравнением с таким же по длине
предыдущим периодом. `backend/app/services/dashboard_service.py` — это
**только агрегатор**, он не собирает новых данных и не заменяет отдельные
страницы: каждый блок ниже — самостоятельный `has_data`, независимый от
других, поскольку берётся из своего, уже существующего источника:

- **Заказы и выручка** — сумма `ordered_units`/`ordered_sum_actual_price_rub`
  из `ProductCardStatistic` (отчёт «Аналитика → Товары», см. выше) по всему
  магазину — единственный источник в приложении с настоящими заказами/
  выручкой по всем товарам, а не только по рекламируемым. Если этот отчёт
  никогда не загружался — блок пустой, с прямой ссылкой на страницу «Товары».
- **Реклама** — расход из обоих источников (автосбор через Performance API и
  ручная CSV-загрузка), показаны раздельно по той же причине, что и на
  странице «Реклама» (сложение рискует задвоить расход, если оба источника
  покрывают одни и те же кампании/период). «Доля расходов на рекламу в
  выручке» — это **новая, отдельная метрика**, которую не стоит путать с ДРР
  по кампаниям на странице «Реклама»: она делит суммарный расход на рекламу
  на **всю** выручку магазина (все каналы, из блока выше), а не только на
  «продажи в продвижении» — именно так владельцы обычно и формулируют вопрос
  «какой процент выручки уходит на рекламу». Настоящий ROI (с учётом
  себестоимости товара) показать нельзя — приложение нигде не собирает данные
  о себестоимости.
- **Отзывы** — количество новых отзывов за период (по `published_at`) и
  средний рейтинг за период (текущий и предыдущий, для сравнения тренда, а не
  день-к-дню), плюс отдельно — количество отзывов без ответа **на текущий
  момент** (это очередь работы, а не показатель именно этого периода).

Как и у остальных отчётов, сравнение с предыдущим периодом — это сумма за
весь период против суммы за такой же по длине предыдущий период, а не
день-к-дню: у сводки по всему магазину период обычно недели/месяц, и
сравнивать с одним произвольным днём было бы куда более шумно.

## Интеграция с Yandex AI Studio

`backend/app/services/ai/` реализует провайдер-независимый интерфейс `AIProvider`
(`analyze_review`, `generate_review_reply`, `rewrite_review_reply`,
`analyze_reviews_batch`, `check_connection`); бизнес-логика никогда не обращается к
конкретному провайдеру напрямую. `YandexAIProvider` использует OpenAI-совместимый
Responses API Yandex AI Studio (`https://ai.api.cloud.yandex.net/v1/responses`,
заголовок `Authorization: Api-Key ...`, модель — URI `gpt://<folder_id>/<model>`).
Ответ модели валидируется через Pydantic; при невалидном JSON выполняется один запрос
на исправление формата, после чего при неудаче ответ не создаётся и не публикуется.
Перед отправкой текста отзыва в ИИ телефоны, email и номера заказов маскируются.

Архитектура позволяет добавить `GigaChatProvider`, `OpenAIProvider`,
`ProxyAPIProvider`, `RouterAIProvider`, не меняя вызывающий код.
